搭博客这件事,真正麻烦的从来不是"用哪个工具",而是先想清楚自己打算怎么用它。我花了半天时间在三个候选之间来回比较,最后发现决定权不在功能表上,在一句很朴素的话里:

**我以后会不会反复改页面。**

答案是不会。页面配置一次,之后大概率几个月不碰。这句话直接把天平的走向定死了,下面说为什么。

<!--more-->

## 三个候选,三种设计哲学

| | Hugo | Hexo | Astro |
|---|---|---|---|
| 运行时依赖 | 无,单个 exe | Node + node_modules | Node + node_modules |
| 构建 1000 篇 | 1 秒内 | 分钟级 | 数十秒 |
| 模板语言 | Go template | EJS / Pug | HTML + JS 表达式 |
| 内容校验 | 无 | 无 | Zod schema |
| 主题生态 | 成熟,偏英文 | 最全,中文文档最多 | 少而精 |
| 加交互组件 | 手写 JS | 插件 | 岛屿架构 |
| 长期维护 | 几乎无损 | 旧插件易坏 | 版本迭代快 |

看完这张表,很容易得出"看需求选"这种废话。真正有用的是把它拆成两类成本:**一次性成本**和**每天都在付的成本**。

- 模板难改、语法反直觉 —— 一次性。你配好之后不碰,这个成本就摊薄到接近零。
- 构建慢、依赖装不上 —— 每天都付。哪怕只慢十几秒,一天预览二十次就是五分钟,外加每次等待时被打断的思路。

Hugo 的缺点全在第一类,Hexo 和 Astro 的缺点全在第二类。而我的用法是"配一次,写很久",所以答案很清楚。

## 那个 0.1 秒的差别

这个数字值得单独说。Hugo 的 `server` 模式在文件保存的瞬间完成重建并热替换,实测改一行字到浏览器刷新完成,不到一百毫秒 —— 快到你的眼睛还没从编辑器移到浏览器,页面已经变了。

这件事的意义不在效率,在**心流**。写作时有大量"我改一下看看"的动作:换个措辞、加个小标题、调一下代码块的语言标记。如果每次都要等十几秒,你会下意识地攒着一起改,而攒着的结果通常是忘了要改什么。

Hexo 是另一种情况。它的 `generate` 是全量渲染,几百篇文章时预览一次要半分钟以上。有人会说"我又不是天天写",但恰恰是"偶尔写"的人更难受 —— 你不熟练,所以更依赖即时反馈。

## 代价说清楚:Go template 是个坑

选 Hugo 不是没有付出。它的模板语言不是"长得像 HTML 的模板",而是一套独立的表达式语言:

```go-html-template
{{ range .Site.RegularPages.ByDate.Reverse }}
  <article>
    <h2><a href="{{ .RelPermalink }}">{{ .Title }}</a></h2>
    <time>{{ .Date.Format "2006-01-02" }}</time>
    {{ with .Params.image }}
      <img src="{{ . | relURL }}" alt="">
    {{ end }}
  </article>
{{ end }}
```

几个真实会咬人的地方:

1. **字段名拼错不报错**。`.Params.cover` 写成 `.Param.cover`,渲染结果就是空白,页面正常输出,你只能靠肉眼找。
2. **日期格式是 Go 的参考时间**,`"2006-01-02"` 而不是 `"yyyy-MM-dd"`。第一次见会以为是乱码。
3. **上下文 `$` 和 `.` 的区别**。在 `range` 里面,`.` 是当前项,想访问站点级数据得写 `$`。这个规则不直观,报错信息也不解释。

所以结论是:**Hugo 适合"用主题"的人,不适合"写主题"的人。** 如果你打算从零手写一套模板,Go template 会持续消耗你;如果你只是挑一个主题、改改配色和字体,那点语法你永远不用碰。

## 关于"文艺"的一个纠正

一开始我以为"文艺"要靠框架选得好。后来发现不是 —— 排版观感几乎全部来自主题本身:衬线字体配多大的行高、留白留多少、卡片圆角几个像素、配色偏冷还是偏暖。这些和底层是 Hugo 还是 Astro 没有关系。

所以真正该挑的是主题,不是框架。Hugo 这边 Stack 和 Blowfish 都做得很好,中文社区的 Hexo 用 Butterfly 更多是因为它是中文文档,不是因为技术更合适。

框架只决定一件事:**你以后改动的上限在哪里**。Astro 的上限更高(能加组件、能写逻辑),Hugo 的上限更低但足够。

## 什么时候不该选 Hugo

诚实地说三种情况:

- 你需要在文章里嵌交互组件(投票、可拖拽的图表、小游戏)。Astro 的岛屿架构天然支持,Hugo 要手写一堆 vanilla JS。
- 你想要"说说、相册、看板娘"这类站内小功能。Hexo 的 Butterfly 主题现成就有,Hugo 得自己拼。
- 你完全不想碰命令行。那静态博客都不适合,去用现成平台。

除这三种之外,一个以文字为主的博客,Hugo 很难选错。

## 部署

GitHub Pages 免费,配一个 Actions 流水线,`git push` 之后自动构建发布,全程十几秒。配置文件在仓库的 `.github/workflows/hugo.yaml`,一次配好后不用再管。

这也是选 Hugo 的一个隐性好处:构建够快,CI 里几乎不占时间额度,而且不需要缓存 node_modules 那套东西。
