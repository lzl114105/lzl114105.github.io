面试口述要点：简短讲清「问题背景 → 我的决策 → 备选方案 → 代价/风险」，贴合文档 ADR 决策记录思路，不要大段背诵。

## 一、业务与需求理解

### Q1：这个项目是不是简单的报表看板系统？业务本质是什么？

并不是简单的查询看板系统，本质是一套**数据飞轮系统**。

- 链路：用户 IP 对话原始会话文本 → AI 抽取结构化标签画像 → 两条消费路径。
- 路径一：供给在线对话服务，让 IP 角色跨天记住用户，提升体验。
- 路径二：供给运营做看板、人群圈选，支撑运营决策。

核心价值闭环是画像结果反哺在线对话；只做运营看板，系统价值直接减半。需求里的矛盾要理解为：写是毫秒级实时落会话，分析是离线，业务要求第二天记住用户，因此是**离线写、在线读**的读写分离——批处理产出快照，在线走低延迟缓存读取，批处理结果不能直接暴露给在线链路。

### Q2：需求里「离线分析」和「第二天记住用户」存在矛盾，怎么理解？

- 实时对话毫秒级将会话入库；T+1 离线批处理生产画像快照（离线写）；在线对话服务通过独立低延迟缓存通道读取画像（在线读）。
- 主链路 T+1，06 点前画像就绪，满足第二天记住用户；近线分钟级通道是可选补偿，仅改善当天体验，**不作为真相源，不参与看板统计**。
- 不能把批处理输出直接给在线：批处理延迟高，无法满足在线 P99 ≤ 20ms 的性能约束。

### Q3：项目北极星指标是什么，为什么选它，不用任务成功率？

北极星指标：**画像有效覆盖率**。定义：过去 7 天活跃用户中，拥有 ≥3 个置信度 0.7 以上高置信标签的用户占比。

单纯任务成功率只代表任务跑成功，不代表标签质量高；这个指标同时约束时效（数据要新）、用户覆盖、标签质量置信度，更能反映业务真实价值。

### Q4：两类消费方是谁，访问模式差异，带来什么架构约束？

- **IP 角色在线运行时**：单点高频点查，每个用户对话都要读画像；要求 P99 ≤ 20ms，不能阻塞主对话链路。
- **运营人员**：群体聚合、人群圈选、用户下钻；低频，交互式查询秒级即可。

第一性约束：**存储分层，并且看板、用户详情必须同源，共用同一套画像快照，禁止两套独立聚合链路**。否则会出现看板统计人数与下钻筛选人数对不上的口径 bug。

### Q5：标签为什么区分全局标签和 IP 角色局部标签？

一个用户会和多个不同 IP 角色聊天，用户对角色 A 说的偏好不应被角色 B 拿到。全部使用全局标签会出现隐私泄露的体验事故。存储主键设计为 user_id + ip_role_id，支持角色局部标签，同时支持跨角色的用户维度聚合视图。

### Q6：标签元属性有哪些？标签时效衰减业务场景举例

每个用户标签实例元属性：confidence 置信度、source 来源、evidence 证据消息 ID、first_seen/last_seen 首次末次命中、hit_count 命中次数、status 生命周期状态。

标签分 4 个时效等级：永久、长时 30 天、短时 7 天、瞬时。举例：用户三个月前提过喜欢喝拿铁，后续再也没聊过，不能让 IP 角色一直反复提起；需按半衰期衰减，分数逐步降低，到期失效。瞬时标签仅用于本次会话增强，不写入长期画像。

### Q7：双层标签治理逻辑，为什么不让 LLM 自由生成全部标签？

双层：①核心封闭字典；②开放候选池。完全放开大模型自由生成会出现标签爆炸，大量同义、零散标签，运营看板无法聚合使用。

- LLM 产出的陌生标签先进候选池，只展示在用户详情页，**不进入看板聚合**。
- 通过频次统计、向量聚类做同义合并，人工审核后提升为正式字典标签，才参与看板统计。
- 废弃标签不删除历史数据，只标记失效。

### Q8：38 项边界条件，风险最高的 3 个是什么？

任务幂等与重跑、标签冲突消解与时效衰减、看板和用户维度口径一致性。这三类开发阶段容易忽略，上线故障后果严重。

### Q9：14 个待澄清 Q1-Q14，哪几个必须评审确认，不确认不能开工？默认假设？

Q1 真实业务规模 DAU；Q2 时效要求（要不要近线通道）；Q12 LLM 成本预算上限。这三个直接决定架构选型、分片策略、分级路由参数。默认假设：DAU 80 万；以 T+1 为主，近线可选；标签字典业务预定义 + 候选池人工确认。

## 二、整体架构与 ADR 架构决策

### Q1：五层架构介绍，编排层为什么独立？xxl-job + 定时脚本行不行？

五层：接入层、存储层、计算层、编排层、服务层。编排层承担批次、分片、任务队列、Worker 执行、重试死信、背压、进度统计。

普通定时脚本、XXL-Job 只能做到定时触发执行，缺少业务语义：分片粒度重试、精确进度统计、租约僵尸任务回收、背压、部分成功状态。需求 F5 要求进度误差 ≤2%、分片重跑、任务可暂停取消，通用调度框架做不到，因此编排层独立。

### Q2：部署单元只有 3 个，为什么不做大量微服务？哪个必须物理隔离？

3 个部署单元：admin-api 管理接口、analyze-worker 分析消费、scheduler 调度中心。过早微服务会带来分布式事务、链路追踪、运维复杂度，当前 80 万 DAU 规模不需要。**analyze-worker 必须物理隔离**：它是 IO 密集，大量调用大模型 API，若与管理端混部，分析流量风暴会打挂运营管理接口。

### Q3：画像存储选型，为什么不用宽表？标签事实快照放 MySQL，会话明细放 ClickHouse，画像为什么不放 ClickHouse？

- 标签集合持续新增迭代，若用数据库宽表就要频繁 DDL 改 schema，维护成本极高。
- 标签事实、画像是小数据，强事务、高频单点查询，适合 MySQL；会话明细 TB 级别、大量聚合统计，适合 ClickHouse 列存。
- ClickHouse 不擅长高频小更新、高并发单点查询；画像需频繁更新标签置信度、状态，放 ClickHouse 性能很差。

### Q4：ADR-4 看板和用户维度共用画像快照，不这么做会发生什么？

会出现口径不一致经典故障：看板统计夜猫子用户 12 万，点开用户详情筛选，筛选出来不是 12 万人。解决方案：看板指标全部由画像快照聚合生成，禁止单独旁路聚合链路。

### Q5：近线通道定位？T+1 + 近线双链路并发写，如何解决乱序？三重机制

近线通道定位是**体验补偿，不是真相源**；产出临时标签，不写入正式快照，不参与看板统计；是否开启看业务 Q2 确认。双链路乱序三重机制：

1. **单调 epoch 条件更新**：近线 epoch 用会话事件时间戳；T+1 批次 epoch 是批次调度时间戳（更大）；只有 epoch 更大才允许更新画像，天然防乱序。
2. **合并更新而非覆盖**：新标签 merge 进旧集合；同标签取高置信度、更新 last_seen；未命中的旧标签不删除，依靠时间衰减。
3. **T+1 离线快照是权威源**，近线产生的偏差会被 T+1 批次修正。

### Q6：首期为什么不引入向量数据库，什么条件才引入？

标签候选池的聚类归并是**离线批量矩阵计算**，单机 NumPy 矩阵运算分钟级完成，不需要在线 ANN 检索；引入向量数据库带来运维成本却无收益。触发引入条件：①需要运营在线语义检索标签；②话题数据量增长到千万级。

### Q7：人群圈选为什么选 Roaring Bitmap？直接存 userId 列表有什么问题？

Roaring Bitmap 集合交并差运算毫秒级，存储体积很小。直接存 userId 列表：圈选交集并集需把大量 ID 拉到应用内存做集合运算，内存压力大；用 SQL IN 查询会打爆数据库。

### Q8：Kafka 做消息队列，备选 RocketMQ，切换 RocketMQ 架构改动大吗？

本方案任务状态持久化 MySQL，MQ 只做通知，**不依赖 MQ 原生重试、死信能力**。Kafka 优势：高吞吐、支持重放；RocketMQ 原生延迟消息、死信更友好。切换 RocketMQ，上层编排层契约不需要改动。

## 三、核心模块深挖

### Q1：L0/L1/L2 分级路由，每一层作用、覆盖率，为什么 L0 很关键

- **L0 规则统计**：100% 全量用户；纯计算无模型；产出活跃时段、会话频次等标签；成本几乎可忽略。
- **L1 轻量小模型**：约 30% 活跃用户；产出兴趣、情感极性。
- **L2 大模型**：严格控制 ≤5% 难样本；输出完整结构化标签。

L0 规则层把大量简单统计标签直接算出来，砍掉大量模型调用，是控制 LLM 成本最核心的一环。

### Q2：哪些样本才会走到 L2 大模型？

满足任一：L1 输出置信度过低；命中高风险标签域；用户冷启动标签为空；会话长文本、语义复杂难样本。

### Q3：除分级路由，还有哪些 LLM 成本控制手段？

1. 会话级聚合，不要单条消息调用大模型。
2. 会话摘要缓存复用，避免重复计算。
3. 输入文本压缩，只投喂关键片段。
4. 精简 Prompt 和输出 Schema，控制输出 token。
5. 重跑任务时若会话 hash 不变，直接复用历史结果。
6. 成本监控 + 熔断机制。

### Q4：成本熔断机制，熔断之后数据会丢失吗？

监控当日 LLM 消耗占预算比例：70% 告警；70-90% 自动提升 L1 比例、暂停低优先级重算；>90% 熔断，全部降级 L0+L1。**原始会话明细已经落库不会丢失，任务标记 pending，第二天预算重置后可重新跑批，不会丢数据。**

### Q5：大模型幻觉三道拦截闸门，哪道最重要？校验失败怎么处理？

1. JSON Schema 强制校验，字段、枚举值合法性。
2. **证据原文子串回查（最重要）**：模型返回的 evidence 证据片段，后端校验必须是会话原文子串，防止编造证据。
3. tag_key 必须存在正式标签字典，陌生 key 打入候选池。

校验失败策略：重试一次；仍失败降级 L1 模型，标记 degraded 告警，不写入正式标签库。

### Q6：会话切分规则优先级？跨日归属？超长会话怎么处理？

优先级从高到低：04:00 跨日切分 > 静默 30 分钟断会话 > 话题漂移切分 > 上游会话 ID 变更兜底。跨日会话归属**第一条消息的业务日期**。超长会话：按轮次切分成多个片段，分段生成摘要再聚合；记录截断标记，禁止把几千轮会话全部丢给大模型。

### Q7：标签冲突裁决优先级（先说喜欢咖啡，后面说讨厌咖啡）

优先级：时间加权（更近优先）＞ 置信度 ＞ 证据命中次数 ＞ 来源优先级（人工 ＞ 规则 ＞ 小模型 ＞ 大模型）。无法判定冲突不要强制二选一，保留主标签 + 次多值标签。

### Q8：任务分为 batch 批次、task 分片、subtask 子任务，为什么拆多层？

若只按批次粒度重跑，只要一个用户失败，整个批次全部重跑，浪费大量算力。分层之后：进度统计精确；失败只需重试对应分片/子任务；进度误差控制 ≤2%。

### Q9：任务幂等怎么做？消息重复消费、任务重跑两种场景

两层幂等保障：

- 任务层：幂等键 batch_id + shard_key。
- 数据库层：标签事实表唯一键 user_id, ip_role_id, tag_key, tag_value，使用 INSERT ... ON DUPLICATE KEY UPDATE。
- 画像更新使用 epoch 条件更新，只有更大 epoch 允许写入。

### Q10：Worker 进程被 kill，正在执行的任务怎么办？租约机制？

任务表维护 lease_expire_at 租约过期时间。Worker 拿到任务后持有租约并定时续租。Worker 被杀，租约到期，其他 Worker 扫描到过期租约接管该任务，进入重试队列，任务不会丢失。

### Q11：Kafka 积压，背压机制怎么做？

监控 consumer lag、任务积压量。触发背压：暂停低优先级批次入队；优先保障活跃用户分片；大模型不可用时熔断降级，不能阻塞队列。

### Q12：在线画像三级缓存链路，降级策略，绝对不能干什么？

链路：Caffeine 本地缓存（TTL 5min）→ Redis（TTL 25h）→ MySQL 快照兜底。任何一级故障不能向上抛异常；最差返回空画像或上一版快照；**绝对不能阻塞对话主链路**。接口返回 profile_ver 版本号，方便上游判断画像新鲜度。批次完成增量刷新缓存，不清空全量缓存，防止缓存雪崩。

### Q13：用户注销，级联删除要清理哪些存储？级联删除编排器？

涉及存储：MySQL 标签事实、画像快照；ClickHouse 会话明细；Redis 缓存；人群 Bitmap；对象存储原始消息。统一异步删除编排器，根据 user_id 索引遍历各存储执行删除；SLA 7 天完成；完整留存审计日志，输出删除凭证，满足合规要求。

## 四、故障、性能与容量估算

### Q1：DAU 80 万，容量简单估算

DAU 80 万，人均日轮次 40 轮，每轮 2.2 条消息；日消息 7000 万；日会话 280 万；日原始文本 12GB；会话明细 ClickHouse 年约 1.5TB；标签画像 MySQL 几十 GB。

### Q2：凌晨上游数据延迟，05 点数据还没齐，批次如何处理？

做水位校验，设置等待窗口；超时后产出 partial 部分结果，**显式标记数据不完整，不能静默标记成功**。

### Q3：线上看板和用户详情口径不一致，排查思路

第一步核对两边使用的 batch 批次号、快照版本号；看板和用户详情必须使用同一画像快照。若批次号不一致，就是问题根源；排查是否存在旁路独立聚合链路。

### Q4：大模型 API 雪崩大量超时，系统会不会挂？如何降级？

不会整体挂。模型网关熔断，降级到 L0 规则 + L1 小模型；任务不会阻塞，生成补偿任务；会话原始数据已落库，后续可重跑补齐标签。

### Q5：这个系统除单元、集成测试，还有哪些特殊测试？

1. 混沌故障注入测试：kill worker、Redis 宕机、MQ 阻塞、大模型限流。
2. 成本回归测试：每次发布跑固定样本，校验 token 消耗，防止 Prompt 膨胀带来成本漂移。
3. 边界场景测试：乱序消息、超长会话、用户注销删除。
4. 幂等重跑测试：重复投递任务，验证结果不变。

## 五、项目难点、风险与演进

### Q1：这个项目最大技术难点是什么？（三选一）

- **成本方向（推荐）**：LLM 调用成本是硬约束，不能全量调用大模型。难点是设计 L0/L1/L2 分级路由体系，结合会话聚合、缓存、熔断，把大模型调用压到 5% 以内，同时保证标签质量。
- **数据一致性**：离线 T+1 主链路 + 可选近线补偿链路，双链路并发写画像的乱序问题；用 epoch + 合并更新 + T+1 权威源三重机制保证数据可控。
- **任务编排**：实现分片、子任务粒度的任务系统，租约、幂等、背压、精确进度，通用调度框架无法满足业务语义。

### Q2：上线标签准确率没达到 85%，怎么排查优化？

1. 看监控指标：置信度分布、证据缺失率、Schema 校验失败率。
2. 抽样 bad case 人工分析。
3. 调高置信度阈值，低置信标签禁止进入线上画像。
4. 优化 Prompt，调整分级路由策略。
5. bad case 回流作为负样本迭代模型。

### Q3：如果 DAU 不是 80 万，实际 400 万，现有架构哪些要改造？

1. Worker 集群水平扩容。
2. ClickHouse 做分片拆分。
3. MySQL 画像库压力上涨，评估迁移 HBase。
4. 重新核算 LLM 预算，收紧 L2 大模型调用占比。

### Q4：一期不做，后续演进条件？

1. 时效要求小于 1 小时：开启近线补偿通道，存储、引擎不用改动。
2. 用户规模暴涨：画像存储迁移 HBase。
3. 需要在线标签语义检索：引入向量数据库。
4. Prompt 模型迭代频繁：LLM 抽取层拆独立 Python 服务。

## 六、挖坑题（面试官故意测试）

### Q1：既然近线可以分钟级产出画像，直接全部用近线，抛弃 T+1 行不行？

不行。全量近线会带来巨大 LLM 调用成本；乱序问题被放大；近线不能作为真相源，看板统计口径很难保证；T+1 批处理是唯一真相源。

### Q2：标签事实直接放 ClickHouse，在线画像直接查询 ClickHouse 行不行？

不行。画像需要高频小更新、高并发单点查询，ClickHouse 不适合这个场景，会出现性能灾难。

### Q3：模型返回的 evidence 证据字段，直接相信模型输出，不用后端校验可以吗？

不行，大模型会编造虚假证据。必须后端做原文子串校验，否则幻觉直接污染线上画像。

### Q4：全部依赖 Kafka 消息，如果 Kafka 挂掉，任务全部丢失？

不会。ADR-5 任务状态持久化 MySQL，MQ 只做通知。Kafka 恢复后扫描任务表重新投递消息，任务不会丢失。
